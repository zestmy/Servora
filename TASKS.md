- 2026-07-29 — Settings > Users "Last Active" showed times in the FUTURE ("7 hours from now") and "Never" for recently-seen users. ROOT CAUSE of the future times: the column was resolved inside SQL via `COALESCE(UNIX_TIMESTAMP(users.last_active_at), 0)`. last_active_at is a naive DATETIME holding an Asia/Kuala_Lumpur wall clock (PHP writes it), but UNIX_TIMESTAMP() reinterprets that string in MySQL's OWN session timezone — and config/database.php sets no connection timezone, so MySQL falls back to SYSTEM = the VPS clock = UTC. Every heartbeat therefore read back 8 hours late; a user active 30 min ago rendered as "7 hours from now". Never reproduced locally because this dev box's MySQL SYSTEM tz is also +08. FIX: the SQL subselect now returns only sessions.MAX(last_activity) (a genuine unix timestamp, so timezone-safe), and last_active_at is merged in PHP through the Eloquent datetime cast — same approach Admin\Users already used correctly — with the later of the two winning. Reproduced the exact failure in a harness by forcing `SET time_zone='+00:00'`: old expression → "7 hours from now", new path → "30 minutes ago" with a correct tooltip. TWO RELATED DEFECTS fixed alongside: (a) the blade built its Carbon with `createFromTimestamp()` with no timezone argument, which yields a UTC-rendered instance — diffForHumans was fine (absolute) but the hover `d M Y, h:i A` tooltip was 8 hours out; both this blade and Admin\Users now pass config('app.timezone'); (b) TouchLastActive ran AFTER SetDisplayTimezone in bootstrap/app.php, so on GET requests the heartbeat was stamped in the VIEWER's timezone — users with a custom timezone wrote wall clocks on a different basis than everyone else, making the column incomparable; the web(append:) order is now SetPermissionsTeamFromCompany → EnsureAccountActive → TouchLastActive → SetDisplayTimezone, so nothing that persists a timestamp runs under a shifted clock (verified neither reordered middleware reads the clock). "NEVER" is NOT a bug: it means both sources are genuinely empty — the DB sessions fallback went stale when production sessions moved to Redis (2026-06-29) and last_active_at only began recording 2026-07-28, so anyone whose last visit fell in that gap has nothing stored. Self-heals on their next request; the label now reads "No activity recorded" with a tooltip explaining tracking started 28 Jul 2026, instead of asserting the user never logged in. Note: production could not be inspected directly — the SSH read was blocked by the permission classifier, so the UTC diagnosis is inferred from the mechanism plus the reported 7-hour offset. No migration. Deployed
